Angela 一次请求怎么走：数据结构与它们的关系

本文描述提交 c789ff55 的代码，是《启动过程》的续篇。行号可能随代码演进而漂移，以函数名为准。

一句话概括

你按下回车后，这句话会依次经过下面几站，最后变成屏幕上的回答：

  1. 界面把它交给工作区，工作区交给协调器。
  2. 协调器为这个会话现场组装好智能体，再交给会话执行器。
  3. 执行器把你的话存成一条消息，连同历史一起发给大模型。
  4. 大模型每吐出一点内容，执行器就更新数据库里的消息。消息服务随即发出事件，界面据此刷新。
  5. 大模型请求工具时，工具执行的结果也存成消息，再发回给大模型。如此往复，直到大模型说完。

整个过程中，数据库里的消息是唯一的事实来源。界面看到的一切，都是消息被创建或更新时发出的事件。

本文以本地模式为准。工具调用经过的三层关卡在前面的讲解里已经介绍过，这里只讲它们在一轮对话里的位置。

核心数据结构

先认识四个数据结构，后面的流程都围绕它们转。

消息 Message

定义在 internal/message/content.go:226。

字段含义
ID唯一编号，创建时生成的 UUID
Role谁说的话，见下表
SessionID属于哪个会话
Parts内容片段列表，见下表
Model Provider Agent由哪个模型、哪家服务商、哪个智能体产生
CreatedAt UpdatedAt时间戳，单位毫秒
IsSummaryMessage是否为压缩上下文时生成的摘要

角色有四种，定义在 content.go:23 到 28。

角色含义
user你说的话。系统提醒也用这个角色存储
assistant大模型说的话，包括它请求的工具调用
tool一次工具调用的结果
system程序插入的说明，比如"已切换到某某智能体"

内容片段是一个接口 ContentPart，定义在 content.go:62。它只有一个私有方法，作用是把下面这些类型标记为"可以放进消息里"。

类型内容出现在
TextContent一段文字用户消息、助手消息
ReasoningContent模型的思考过程，以及部分服务商要求回传的签名助手消息
BinaryContent附件，比如你粘贴的图片用户消息
ImageURLContent图片链接用户消息
ToolCall工具调用：编号、工具名、参数 JSON、是否已接收完整助手消息
ToolResult工具结果：对应的调用编号、内容、是否出错工具消息
Finish结束标记：结束原因、时间、本步的 token 用量每条消息的末尾
ShellCommand你在输入框里直接执行的 shell 命令及输出用户消息

定义见 content.go:66 到 175。

结束原因定义在 content.go:46 到 60。

取值含义
end_turn模型说完了
tool_use模型请求了工具，还会有下一步
max_tokens输出长度到了上限，被截断
canceled你按了取消
error出错，比如服务商返回错误
content_filter服务商的安全过滤拒绝回答

消息在数据库里的样子

消息表建于 internal/db/migrations/20250424200609_initial.sql:47。内容片段不拆成多列，而是整体序列化成 JSON 存在 parts 这一列里。每个片段被包成 {"type": ..., "data": ...} 的形式，类型标签定义在 internal/message/message.go:638 到 647，序列化函数是 marshalParts，见 message.go:654。

例如，模型请求读取一个文件时，助手消息的 parts 列大致如下。字段名来自结构体的 JSON 标签，具体数值是示意。

[
  {"type": "text",
   "data": {"text": "我先看一下 README。"}},
  {"type": "tool_call",
   "data": {"id": "toolu_01", "name": "Read",
            "input": "{\"file_path\":\"/home/me/shop/README.md\"}",
            "provider_executed": false, "finished": true}},
  {"type": "finish",
   "data": {"reason": "tool_use", "time": 1791273600,
            "output_tokens": 58}}
]

会话 Session

定义在 internal/session/session.go:59。一轮对话中会读写的字段如下。

字段含义
ID Title编号和标题。标题由第一句话自动生成
ParentSessionID子智能体的会话会指向派它出去的父会话
ActiveAgent这个会话选了哪个智能体和模型，上一轮讲解里讲过
PromptTokens CompletionTokens当前上下文用了多少 token，用来判断是否需要压缩
Cost累计花费
SummaryMessageID最近一次压缩生成的摘要消息。加载历史时从这条开始
Todos智能体维护的待办列表
MessageCount消息数，由数据库触发器自动维护

MessageCount 不需要代码手动加减。插入或删除消息时，数据库触发器会自动更新它，见 initial.sql:68 到 82。

一轮的调用参数 SessionAgentCall

定义在 internal/agent/agent.go:147。协调器把一轮需要的一切装进这个结构体，交给会话执行器。

字段含义
SessionID在哪个会话里跑
Prompt Attachments你说的话和附件
Agent本轮的智能体，包含模型、工具列表、系统提示。整轮不可变
Compact上下文快满时用来做摘要的智能体
RunID调用方给的编号，本轮结束事件会原样带回
ProviderOptions 和采样参数温度、TopP 等，发给大模型的参数
本轮的智能体不可变。 注释写明，Agent 字段在一轮开始时解析好，整轮都不能改。配置变化只在下一轮生效，见 agent.go:149 到 151。

运行状态 runState

定义在 internal/agent/run_state.go:18，内嵌在会话执行器里。它记录每个会话"现在能不能跑"。注释说明这里不做任何数据库或大模型调用，只管并发状态，见 run_state.go:14 到 17。

字段含义
activeRequests会话编号到"取消函数"的映射。有条目就说明这个会话正在跑
messageQueue会话编号到排队调用列表的映射。会话忙时，新消息排在这里
dispatchMu每个会话一把锁，保证"判断忙不忙"和"登记为正在跑"是原子的
cancelMark acceptedRuns处理"取消和排队同时发生"的记账：取消落在排队消息交给下一轮的空档里时，靠它们让取消不被漏掉，见 agent.go:1637 和 agent.go:1703

一次请求，一步一步

下面跟踪一个具体场景：你在项目 ~/code/shop 里新开一个会话，输入"README 里有拼写错误，帮我改掉"。模型会先读文件，再改文件，最后回答。

第 1 步：界面发出请求

入口是 internal/ui/model/ui.go:5076 的 sendMessage。

  1. 如果你正在看子智能体的记录，拒绝发送，见 ui.go:5077。
  2. 如果后端还没准备好，比如没有配置模型，报错，见 ui.go:5080。
  3. 没有会话就先建一个，标题暂定为 "New Session"，见 ui.go:5092 到 5105。
  4. 先把界面标记为"忙"，这样你紧接着按 Esc 能正确取消，见 ui.go:5124。
  5. 在后台调用 Workspace.AgentRun，见 ui.go:5136。

AgentRun 会一直阻塞到这一轮结束。注释说明，这就是它放在后台命令里执行的原因，见 ui.go:5328 到 5333。成功返回 agentRunSubmittedMsg，失败返回 agentRunFailedMsg。

这一步没有把你的话直接画到屏幕上。屏幕上出现你的话，要等第 4 步消息写进数据库并发出事件之后。

数据此时是：一个会话编号、一段文字 "README 里有拼写错误，帮我改掉"、空的附件列表。

第 2 步：协调器解析智能体

AppWorkspace.AgentRun 直接调用 coordinator.Run，见 internal/workspace/app_workspace.go:152。真正的逻辑在 internal/agent/coordinator.go:375 的 run。

  1. 交互模式不等 MCP 连完。还在连接的 MCP 服务器这一轮看不到，见 coordinator.go:376 到 394 的注释。
  2. 让子智能体登记表和当前配置保持一致，见 coordinator.go:400。
  3. 调用 turnExecutorFor，得到执行器和本轮的智能体，见 coordinator.go:402。这一步读出会话选的智能体，再现场构建模型、工具和系统提示。上一轮讲解已经讲过。
  4. 合并采样参数，准备压缩用的智能体，必要时刷新登录令牌，见 coordinator.go:416 到 423。
  5. 把一切装进 SessionAgentCall，调用执行器的 Run，见 coordinator.go:450。

数据此时是：一个 SessionAgentCall，里面的 Agent 已经包含 coder 的模型、完整的工具列表和系统提示。

第 3 步：抢占会话或排队

进入 internal/agent/agent.go:591 的 sessionAgent.Run。

  1. 检查参数：必须有文字或附件，必须有会话编号，见 agent.go:592。
  2. 拿到这个会话的派发锁，见 agent.go:613 到 614。
  3. 如果会话正忙，把这次调用放进 messageQueue，解锁，直接返回，见 agent.go:645 到 663。排队的消息之后会被处理，见第 7 步。
  4. 如果会话空闲，创建一个可取消的上下文，把取消函数登记进 activeRequests，再解锁，见 agent.go:665 到 680。从这一刻起，会话就是"忙"的。
为什么要在锁里登记。 注释解释，"判断忙不忙"和"登记为正在跑"必须是一个整体。否则两条几乎同时到达的消息可能都认为会话空闲，在同一个会话上开出两轮，见 agent.go:605 到 612。

函数退出时会撤销登记。撤销用的是"比较后删除"，只删自己登记的那一条，避免误删下一轮的登记，见 agent.go:683 到 687。

第 4 步：准备上下文

仍在 Run 里，按顺序执行：

  1. 拼系统提示。 把已连接 MCP 服务器提供的说明附在系统提示末尾，见 agent.go:695 到 707。
  2. 创建 fantasy 智能体。 传入模型、系统提示和工具列表，见 agent.go:714 到 719。
  3. 读会话和历史消息。 见 agent.go:722 到 730。如果会话压缩过，只从摘要那条开始读，见 agent.go:2264 的 getSessionMessages。
  4. 后台生成标题。 如果这是会话里第一句真正的用户输入，开一条协程去生成标题。它用的上下文不随本轮取消，因为生成标题可能要几十秒，见 agent.go:732 到 739。
  5. 登记收尾动作。 用 defer 注册第 7 步的收尾，见 agent.go:771。
  6. 转换历史。 把数据库里的消息转换成 fantasy 能理解的格式，见 agent.go:805。转换时会丢掉缺了另一半的工具调用或结果。如果模型不支持图片，还会去掉图片。后两点来自代理报告，未逐行核对
  7. 插入系统提醒。 比如"你很久没更新待办了"，存成 user 角色的消息，见 agent.go:816 到 837。
  8. 存下你的话。 调用 createUserMessage，见 agent.go:842。它创建一条 user 消息，内容是一个文字片段，每个附件再加一个二进制片段，见 agent.go:1993 到 2003。

第 8 步的写库会触发一次"消息已创建"事件，你的话就在这时出现在屏幕上。

系统提醒为什么要存进数据库。 注释解释，如果只在内存里临时拼进去，下一轮重算时位置可能不同。发给大模型的前缀一变，服务商那边的提示缓存就失效了。存进数据库后位置固定，前缀每轮都一样，见 agent.go:807 到 815。

非助手消息在写库时会被自动补上一个结束标记，见 internal/message/message.go:194 到 198。所以你在数据库里看到的每条用户消息末尾都有一个 finish 片段。

第 5 步：交给大模型

调用 agent.Stream，见 agent.go:885。传入的东西有：

  • 本轮的话，加上文本附件的内容。
  • 历史消息，也就是第 4 步转换好的列表。
  • 采样参数和服务商专属选项。
  • 最多重试次数，取自常量 streamMaxRetries，见 agent.go:877。
  • 一组回调函数，见下一步。

从这里开始，"请求模型、执行工具、再请求模型"的循环由 fantasy 库驱动。Angela 自己的代码只通过回调参与。fantasy 内部怎么调度，本文没有展开，因为它不在这个仓库里。

第 6 步：每一步的回调

拿前面的场景举例，这一轮会有三步：读文件、改文件、回答。每一步都会触发下面这些回调。

步开始：PrepareStep

见 agent.go:897 到 965。

  1. 使用最新的工具列表，见 agent.go:904。
  2. 把排队的消息并进来。 如果你在模型干活时又发了一句话，它会在这里被存成用户消息，加进本步要发的消息列表，见 agent.go:917 到 926。
  3. 标记提示缓存的断点，见 agent.go:930 到 932。
  4. 创建一条空的助手消息，见 agent.go:943 到 949。之后这一步的所有输出都追加到它上面。
  5. 把这条消息的编号放进上下文，工具执行时可以取到，见 agent.go:953。

每一步都有自己的助手消息。 所以三步就会产生三条助手消息，而不是一条越写越长的消息。

流式输出：OnTextDelta 和 OnReasoning 系列

模型每吐出一小段文字，OnTextDelta 就把它追加到当前助手消息的文字片段上，然后调用 messages.Update，见 agent.go:994 到 1004。思考过程走 OnReasoningStart、OnReasoningDelta、OnReasoningEnd，追加到思考片段上，见 agent.go:966 到 993。

请求工具：OnToolInputStart 和 OnToolCall

  1. 模型刚开始写工具参数时，OnToolInputStart 先加一个未完成的工具调用片段，让界面能立刻显示"正在调用 Read"，见 agent.go:1005 到 1016。
  2. 参数接收完整后，OnToolCall 把它更新为完成状态，并带上参数 JSON，见 agent.go:1064 到 1085。参数不是合法 JSON 时会先被清理，并记下这次调用，结果会被替换成错误提示，见 agent.go:1065 到 1068 和 1088 到 1091。

这两个回调写库时用的是外层上下文，不是本轮可取消的上下文。注释说明，这样即使你中途取消，工具调用也能写进数据库，见 agent.go:1013 到 1015。

执行工具

fantasy 调用工具的 Run 方法。工具外面套着安全、钩子、权限三层，在 internal/agent/coordinator.go:1101 到 1119 组装。需要你确认的操作会在这里弹窗，并一直等到你回答。

工具通过上下文拿到会话编号和消息编号。键定义在 internal/agent/tools/tools.go:21 到 30，取值函数是 GetSessionFromContext 和 GetMessageFromContext，见 tools.go:46 和 51。

工具结果：OnToolResult

把 fantasy 的结果转换成 ToolResult 片段，创建一条新的 tool 角色消息，见 agent.go:1086 到 1101。工具结果不追加到助手消息上，而是独立成一条消息。

步结束：OnStepFinish

见 agent.go:1108 到 1197。

  1. 把 fantasy 的结束原因翻译成 Angela 的结束原因，见 agent.go:1112 到 1131。
  2. 如果某个工具要求停止本轮，比如钩子叫停，就把结束原因改成 end_turn，见 agent.go:1132 到 1149。
  3. 给助手消息加上结束标记，见 agent.go:1155。
  4. 记录本步的 token 用量，累加到会话上，然后保存会话，见 agent.go:1159 到 1195。
  5. 最后更新一次助手消息，见 agent.go:1196。

停止条件：StopWhen

fantasy 每步结束后会检查两个条件，满足任何一个就不再继续，见 agent.go:1198 到 1222。

  • 上下文快满了。 剩余空间小于预留值且开启了自动压缩，就停下来，标记需要压缩。
  • 模型在原地打转。 检测到重复的工具调用，就停下来。

Update 的防抖

流式输出时 Update 被调用得非常频繁。消息服务不会每次都写库，而是把最新状态攒在内存里，最多等 33 毫秒再一次性写入并发出事件，见 internal/message/message.go:22 和 308 到 364。

结构性的变化不等待，会立刻写库。按注释的说法，这包括结束一条消息、增加或完成工具调用、结束一段思考，见 message.go:35 到 41。

第 7 步：这一轮结束

Stream 返回后，Run 根据结果收尾。

出错或取消

如果 Stream 返回错误，代码会把残局收拾干净，见 agent.go:1227 起：

  • 补全未完成的工具调用。 已经发起但还没完成的工具调用，会被标记为完成。
  • 补上缺失的结果。 有调用却没有结果的，会补一条错误结果。
  • 写上结束原因。 取消记为 canceled，服务商出错记为 error。

这样数据库里的对话记录始终是成对完整的，下一轮转换历史时不会出错。未完成的调用参数会被填成空对象，补上的结果内容会注明是出错还是被你取消，见 agent.go:1265 到 1311。这些写库操作用一个不受取消影响的上下文，最多等 5 秒，见 agent.go:1248 到 1256。

需要压缩

如果停止原因是上下文快满，Run 会调用 Summarize 生成摘要，见 agent.go:1376 到 1406。如果被打断时模型还有工具没调用完，代码会先把"继续刚才的请求"排进队列，摘要做完后接着跑，见 agent.go:1388 到 1405。摘要消息的编号会记到会话上，下次加载历史就从摘要开始。最后一句来自代理报告

处理排队的消息

见 agent.go:1475 到 1563。

  1. 拿到派发锁，看排队表里还有没有这个会话的消息。
  2. 没有就清空排队表，返回。
  3. 有就取出第一条，递归调用 Run 跑下一轮，见 agent.go:1563。

排队的消息有两种去向。在第 6 步的 PrepareStep 里，没有 RunID 的排队消息会被并进当前这一轮。带 RunID 的则留在队列里，等这一轮结束后单独跑一轮，见 agent.go:913 到 916 的注释。本地界面发的消息不带 RunID，所以通常会被并进当前轮。原因是界面传入的是空白上下文，见 ui.go:5136；而 RunID 只从上下文里取，见 coordinator.go:448。

延迟的收尾动作

第 4 步登记的 defer 在 Run 退出时执行，见 agent.go:771 到 803：

  1. 把所有攒着的消息更新写进数据库，最多等 5 秒。
  2. 发布一个"本轮结束"事件 RunComplete，里面有会话编号、最后一条助手消息的编号和文字，以及是否出错或取消。

注释解释了这个顺序：先写库再发结束事件，界面就更有可能先看到最后的消息，再看到"结束了"，见 agent.go:762 到 770。如果是递归去跑排队消息，外层不发结束事件，由递归的那一轮来发，见 agent.go:745 到 749。

第 8 步：回到屏幕

每次消息被创建或更新，消息服务都会发布事件。消息服务在 Create 写库后发布"已创建"事件，见 internal/message/message.go:226。事件经过《启动过程》第 7 步讲的事件总线，到达界面的 Update 方法。

界面的处理在 internal/ui/model/ui.go:1066 到 1103：

  • 别的会话的消息，通常是子智能体的，交给专门的函数处理，见 ui.go:1071 到 1076。
  • 已创建：在聊天列表末尾加一项，并重新查询会话是否忙、有没有排队消息，见 ui.go:1079 到 1094。
  • 已更新：刷新对应的那一项，见 ui.go:1095 到 1096。
  • 已删除：从列表里移除，见 ui.go:1097 到 1098。

注释特别说明，"已更新"事件不触发忙碌状态的查询。流式输出时每个字都会触发一次更新，每次都查询会太浪费，见 ui.go:1081 到 1086。

数据库里留下了什么

前面的场景跑完后，这个会话在消息表里新增了这些行。顺序就是创建的顺序。

序号角色内容片段何时创建
1user系统提醒文字、结束标记第 4 步，可能有零到多条
2user"README 里有拼写错误，帮我改掉"、结束标记第 4 步
3assistant思考、文字、Read 工具调用、结束标记 tool_use第一步的 PrepareStep
4toolRead 的结果，即 README 的内容第一步的 OnToolResult
5assistant文字、Edit 工具调用、结束标记 tool_use第二步的 PrepareStep

7assistant"已修正两处拼写错误……"、结束标记 end_turn第三步的 PrepareStep

同时，会话表里这一行的 token 用量和花费被更新了三次，每步一次。会话标题也被后台协程改成了根据第一句话生成的标题。

思考片段只在模型支持并开启思考时出现。场景中模型具体说了什么是示意，消息的角色和片段结构以代码为准。

不变量与约定

  • 数据库是唯一的事实来源。 界面不自己记录对话，只根据消息事件渲染。
  • 一个会话同一时刻只跑一轮。 由派发锁和活动请求表共同保证，见 agent.go:605。
  • 一步对应一条助手消息。 在 PrepareStep 里创建，见 agent.go:943。
  • 工具结果是独立的消息。 角色是 tool，靠调用编号和助手消息里的工具调用配对。
  • 工具调用和结果必须成对。 出错时会补齐，转换历史时会丢掉落单的。
  • 本轮的智能体整轮不变。 见 agent.go:149。
  • 每一轮恰好发布一次结束事件。 递归处理排队消息时，外层不发，见 agent.go:745。
  • 读消息之前要先刷新缓冲。 Update 是最终一致的，直接读数据库可能读到旧状态，见 message.go:43 到 47 的注释。

容易踩坑的地方

  • AgentRun 是同步的。 它要等整轮跑完才返回，失败就在返回值里。不是这个界面发起的那一轮出错时，错误改走事件通知，见 ui.go:948 到 952 和 ui.go:5328 到 5333 的注释。
  • 你的话不是发送时画上屏幕的。 它要等写进数据库、发出事件后才出现。如果写库失败，屏幕上不会有这句话。
  • 系统提醒在数据库里是 user 消息。 查数据库时会看到一些不是你写的 user 消息。界面用 IsReminder 把它们和真正的输入区分开，见 content.go:206。
  • 写库用的上下文不一样。 文字增量用本轮可取消的上下文，工具调用和工具结果用外层上下文。改代码时如果换错，取消时会丢数据，见 agent.go:1013。
  • MCP 工具可能这一轮还没有。 交互模式不等 MCP 连完，刚启动时发的第一句话可能看不到 MCP 工具，见 coordinator.go:376。
  • fantasy 的内部不在本仓库。 重试、步与步之间怎么衔接、工具是否并行执行，都由 fantasy 决定。想深究要去读那个库的源码。
